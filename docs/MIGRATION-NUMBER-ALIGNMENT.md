# 本地提醒迁移编号对齐

合并前，个人开发分支曾使用V53建立user_reminder_read；组员先发布的远端V53至V55用于AI权限、翻译和审计菜单。合并后保留已经发布的V53至V55，将提醒建表脚本顺延为V56，将仅补缺失GI的数据脚本顺延为V57。

## 新数据库及未执行旧提醒V53的数据库

使用当前代码正常启动，Flyway依次执行迁移即可。不要修改已发布的V1至V55，也不要手工创建空的迁移历史或复制其他人的历史记录。

## 已执行旧提醒V53的开发数据库

适用条件必须同时满足：flyway_schema_history中版本53的script是V53__user_reminder_reads.sql；checksum与当前V56__user_reminder_reads.sql的解析校验和完全一致；迁移成功且user_reminder_read表已存在。若版本53是AI权限脚本，此流程不适用。

1. 先完整备份数据库，在独立验证库恢复备份。记录原历史行，不重新执行提醒建表。
2. 仅对校验通过的那一条历史登记，将version从53对齐为56、script改为V56__user_reminder_reads.sql。checksum、执行时间、安装顺序及实际提醒数据保持原样；发现其他历史分歧时停止，不用repair掩盖差异。
3. 在验证库使用本次单独的Flyway运行，临时允许outOfOrder，补齐尚未执行的远端53至55并执行57。前置校验仅允许预期的pending状态，不忽略checksum或失败迁移。
4. 恢复默认outOfOrder=false后再次validate，确认没有待迁移项，再对比核心业务表。验证通过后才对原开发库执行同样操作。

当前工作区开发库已完成上述备份、验证与对齐，57项迁移按默认配置验证通过，14张核心业务表校验和未改变。此处记录迁移冲突处理，不要求更改应用的常规Flyway配置，也不要求在其他数据库无条件执行相同操作。
