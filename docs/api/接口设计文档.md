# 1. 引言

## 1.1. 设计思路

本接口设计面向「AI 控糖助手」微信小程序（C 端）与运营后台（B 端），在数据库 merged-v2（38 张表）之上，采用 RESTful 风格约定资源与 HTTP 动词。C 端前缀 /api/v1，B 端前缀 /admin/v1，网关可分别鉴权与限流。核心思想包括：登录与资料分接口；血糖与饮食分资源并以日看板聚合读取；媒体先上传再引用；OCR/导出异步任务化；AI 对话 SSE 流式返回；枚举统一数字传输，中文仅用于端上展示。

覆盖登录、九时段记录、OCR 确认入库、语音助手、资讯与互动、营养库、反馈、统计、导出与备份、运营管理等能力。错误使用真实 HTTP 状态码（400/401/403/404/409/429/500），响应体 code 与之对齐；不另设「未实现」类业务码。

## 1.2. 设计规范

命名一致性：URL 使用小写连字符名词复数（如 /glucose-records）；JSON 字段 camelCase；数据库列 snake_case。

版本号：在路径中包含主版本，如 /api/v1/…、/admin/v1/…；不兼容变更提升主版本。

报文格式：默认 application/json；charset=UTF-8。上传可使用 multipart/form-data；AI 补全使用 text/event-stream（SSE）。

鉴权：Authorization: Bearer {accessToken}。C 端对应 user_session，B 端对应 ops_session + RBAC perm_code。

统一响应：{ code, message, data, requestId }。成功：HTTP 200 且 code=0。

错误分层：三位 HTTP 表示协议语义；五位 body.code 表示业务细分。各接口输出参数中的 code 不再重复展开，统一以下表为准。

分页：pageNum、pageSize（最大 100）；分页响应统一含 pageNum/pageSize/total/pages/records；字典、轮播、分类等为非分页全量返回。

幂等：聊天消息强制 clientMsgId，重复提交返回已有消息；九时段写入使用 PUT …/by-node，按日期加节点覆盖写入；导出、备份、OCR 创建及运营后台发布/回复/推送执行使用请求头 X-Idempotency-Key，24 小时内同键返回首次结果。

参数规范：路径、Query、Body、请求头分列说明；PATCH 省略字段表示不改，显式 null 表示置空。

口令与密钥：运营口令仅 HTTPS 提交，只存 password_hash（bcrypt/argon2）；禁止明文落库/日志；AI Key、验证码同理。

会话：C 端 Token 默认 7 天（无 refreshToken）；B 端默认 2 小时可滑动续期；登出或禁用将 session.is_valid 置为 0。

参考规约：RESTful 资源导向。

错误码表（HTTP 三位与 body.code 五位对应）：

| HTTP | code | 含义 |
| --- | --- | --- |
| 200 | 0 | 成功 |
| 400 | 40000 | 参数格式、类型或必填校验失败 |
| 400 | 40001 | 业务校验失败或凭证错误 |
| 401 | 40100 | 未登录或 Token 失效 |
| 403 | 40300 | 无权限、账号禁用或注销中 |
| 404 | 40400 | 资源不存在或不属于当前用户 |
| 409 | 40900 | 冲突（唯一键、乐观锁、账号占用） |
| 429 | 42901 | 限流或登录锁定 |
| 500 | 50000 | 系统异常 |

统一成功响应示例：

{ "code": 0, "message": "ok", "data": {}, "requestId": "b1f0c8e2-4a3d-4c1e-9f0a-123456789abc" }

## 4.11~4.13 实现说明（2026-10-15 落地）

> 契约字段未变，这里补"实现怎么落地"的说明，避免只看表格式契约时产生误判。

**权限与页面**

| 项 | 契约写的 | 实际实现 |
| --- | --- | --- |
| 提示词管理页面 | 运营后台 `/ai/config` | **`/ai/prompt`**（菜单 2020，权限 `ai:prompt:list` / 按钮 `ai:prompt:manage` = 2023）。`/ai/config`（菜单 2012，`ai:config:manage`）留给推送模板、对话记忆等其它 AI 配置，**不复用** |
| 场景→模型绑定页面 | 契约未涉及 | 新增 `/ai/scene`（菜单 2021，`ai:scene:list` / `ai:scene:manage` = 2024），接口见下方"场景配置接口" |
| 接口路径 | `/admin/v1/ai-prompt-templates...` | 与契约**完全一致**，仅页面路径不同 |

**版本语义（"版本追加式，不覆盖历史版本"具体指什么）**

1. `POST`（新增）：插入一个新版本，默认 **`status=0` 草稿**——"保存"与"启用"刻意分离；
2. `PATCH /{id}` 且目标行是**草稿**：原地更新（带 `configVersion` 乐观锁）；版本号可以改（目标号未被占用即可）；
3. `PATCH /{id}` 且目标行**已启用**：**不原地改**，按请求内容**追加一个新版本并沿用其启用状态**
   （响应 `appended=true`，旧版本自动停用但保留在列表里，可一键切回）。理由：线上生效的那一版必须始终是只读历史，才能回滚。
   **版本号取值规则**：请求里的 `version` 与基线版本号**相同或留空**时，视为"未指定新版本号"，
   由后端取同场景下一个号；只有显式给出一个**不同的、且未被占用**的版本号时才采用它（已被占用则 409）。
   （2026-10-15 修正：此前把"同号"当成"新版本要叫这个号"，而编辑器打开时表单里正是被编辑那一版的号，
   于是保存必然 409、表现为"点保存后什么都没发生"。）
4. `PATCH /{id}/activate`：启用指定版本并把同场景其它版本停用（库表层面保证"同场景唯一启用"）。
5. `DELETE /{id}?configVersion=`（**契约外的补充接口**，权限同 `ai:prompt:manage`）：删除**草稿**版本（逻辑删除，
   `is_deleted=1` 且写 `deleted_at`，保留可追溯）。**仅允许删 `status=0` 的版本**：生效版本返回 400（删了会让该场景
   静默回落到代码内置提示词，要换线上版本请用 `activate`）；`is_enabled = 0` 写进了 SQL 的 WHERE，
   因此与"启用"并发时也不会误删线上版本。唯一键含 `is_deleted`，删掉之后可以用同一个版本号重建。
   补充这条是因为草稿试错几次就会攒一堆无用版本，而"启用旧版"解决不了列表越来越长。

**阻断式校验（不通过直接 400，坏提示词不入库）**

- 正文非空 + 长度下限（`ai.prompt.min-length`，默认 50 字）；
- 变量名必须是合法标识符，且正文按变量清单**可试渲染**（正文里出现未声明的 `{xxx}`——典型是贴进来的 JSON 示例——会被拒绝）；
- `ai.prompt.safety-scenes`（默认 `chat`）里的场景必须含 `ai.prompt.safety-keywords`（默认 `就医/医院/医生/诊断`）之一；
- 运行时另有一道闸：库表里的启用版本若校验不通过，服务会 WARN 并**退回 classpath 内置提示词**（绕过后台直接写库也炸不了线上）。

**生效时效**：保存/启用成功后本实例立即生效（内部 `refreshNow()`），其它实例最多滞后 60 秒（内容指纹 + TTL 快照）；无需重启。

**出参与契约的差异（均为只读增量字段，不影响契约解析）**：`records[]` 额外返回
`sceneName / versionNo / active / changeNote / configVersion / gmtModified / variables`；
`data` 额外返回 `scenes[]`（四个场景的 `activeVersion`、`activeSource`（`db#id` 或 `classpath`）等，
前端据此显示"当前生效的是哪一版、来自哪里"）。

**场景配置接口（本轮新增，不在原契约中）**

| 接口 | 说明 |
| --- | --- |
| `GET /admin/v1/ai-scenes` | 场景列表：后台绑定值、yaml 兜底值、实际生效模型与来源、可选模型清单。权限 `ai:scene:list` |
| `PUT /admin/v1/ai-scenes/{sceneCode}` | 保存某场景的绑定与参数（`modelCode/temperature/maxTokens/thinking/status/remark`，`clear=true` 表示清空覆盖改回继承）。权限 `ai:scene:manage`。**PUT 是整体覆盖语义：留空 = 继承**，不是"没传就不改" |

生效范围：`temperature / maxTokens` 对文本与视觉场景都走请求级参数生效；
`modelCode` 对文本与视觉场景都生效（视觉场景要求绑定的模型能力含 `vision`，否则保存时直接 400；接口返回 `modelCodeApplies` 恒为 true 并给出说明）；
`thinking` 为 DeepSeek 专有（视觉通道没有该入参，配了不生效，启动时会 WARN）。
优先级统一为 **后台配置（非空字段） > yaml `ai.scenes.<scene>.*` > 通道默认**。
**自 C2 起 yaml 的 `ai.scenes.<scene>.model-code` 已废弃、不再参与选模型**：场景列表里的 `yamlModelCode` 恒为 `null`（字段保留仅为前端兼容），模型只由本接口的 `modelCode` 或通道默认决定。

**能力校验（C3 起是硬校验）**：`PUT` 保存时除「模型存在且启用」外还要求能力匹配——视觉场景的模型能力必须含 `vision`、
文本场景必须含 `text`，否则返回 400 且不落库（此前只是 WARN + 保存，运行时会静默回落，运营以为绑上了）。
`GET` 返回的 `models[]` 每项带 `capability`（`text,tool,stream` / `vision,stream`）与 `capabilityText`（「文本 / 工具 / 流式」），
前端据此把不匹配的模型置灰而不是让它消失（消失会让运营以为模型没配好）。

**运行时诊断**：`GET /admin/v1/ai/runtime/status`（见 4.10.1）逐场景给出实际模型与来源（`binding/default/fallback`），
绑错、通道无默认、视觉默认无显式标记等问题会列在 `issues` 里。

## 5.3 / 5.4 实现说明（2026-10-15 落地，含三条契约外补充接口）

**会话状态语义（契约只给了 0/1/2，没定义区别，这里定死）**

| 值 | 含义 | 谁写它 |
| --- | --- | --- |
| 1 | **进行中**：每用户至多一条（`uk_user_active` 建在生成列 `active_user_id` 上），只有它能继续发消息 | 新建会话 |
| 2 | **已结束**：用户点"新建对话"时，旧会话被置为它 | `POST /current`（forceNew） |
| 0 | **归档**：太久没说话（`ai.chat.archive-idle-days`，默认 30 天） | 列表接口**惰性**标记 |

- 列表默认**全部返回**（含归档），前端可按 `sessionStatus` 过滤或折叠归档；
- 排序：`is_pinned DESC, last_msg_at DESC, id DESC`（置顶优先、其次最近消息、`id` 兜底保证分页稳定）；
- 出参在契约字段（title/last_msg_at/msg_count/is_pinned）之外补了 `id/sessionStatus/sessionType/createdAt/lastMessagePreview`，
  以及 `data.archiveIdleDays`（前端据此解释"为什么这条被归档了"）。`lastMessagePreview` 用一次窗口函数查询批量取回，无 N+1。

**5.4 删除的幂等与越权语义**

- 会话与其消息**同事务**逻辑删除（`is_deleted=1 + deleted_at + deleted_by`），历史数据保留可追溯；
- 三态区分：**不存在 → 404 / 不是自己的 → 404（不泄露存在性）/ 自己的已删除 → 幂等成功**。
  为此专门用了一条绕过 `@TableLogic` 的查询——用普通 `selectById` 会把前两种都变成 null，
  于是"重复删除"要么误报 404（前端重试弹错），要么为了幂等把别人的会话也回成功（把 404/200 变成探测 ID 的信道）；
- 删除当前进行中会话后**不自动补建**：用户下次 `POST /current` 会自然新建一条。

**行为变更（需要注意）**：对**已结束 / 已归档**会话调用 2.24（发消息）或 2.25（补全）现在会被拒绝（40001，文案引导新建对话）。
此前没有这层校验，会出现"消息写进了老会话、但 `/current` 返回的是另一条新会话"这种历史分裂。

**契约外补充的三条接口（页面必需，契约未涉及）**

| 接口 | 说明 |
| --- | --- |
| `POST /api/v1/chat-sessions/current` 增加 `forceNew: true` | "新建对话"。不传时行为与以前完全一致（取或建当前会话）；传 true 时同事务"结束旧会话 + 建新会话"。之所以扩展而不是新开路径：契约里没有"新建会话"，而 `uk_user_active` 决定了新建必须先结束旧的 |
| `GET /api/v1/chat-sessions/{id}/messages?pageSize=&beforeSeq=` | 会话内历史分页（按 `seq_no` 倒序取 N 条后正序返回，`hasMore` + `nextBeforeSeq`）。**注意：返回的是全部历史，与送进模型的记忆窗口（`ai.memory.window-messages`）无关**——用户能翻到很久以前的对话，而模型只看得到最近一小段，这是刻意设计 |
| `PATCH /api/v1/chat-sessions/{id}/pinned` | 置顶/取消置顶（body `{isPinned: true/false}`）。契约只给了 `is_pinned` 字段没给接口，补上是为了不让它变成又一个"死列" |

**新增表 `chat_tool_call`（B3）**：工具调用的元数据（`session_id/user_id/user_msg_id/round_key/tool_name/call_index/ok/duration_ms/error_type`），
**只记"谁被调了、成功与否、耗时、第几次"，不记返回内容**——工具返回里是用户血糖、饮食等健康数据，
落库等于新增一份健康数据副本，权限与脱敏需单独设计；真正的用途（把工具结果回放进上下文）属于记忆阶段。
记录时机是调用发生的当下（不是流结束后统一写）：调用发生过是事实，用户中途取消/本轮报错时最需要留痕。

**`chat_session.window_msg_count` 已废弃（V21 标注）**：该列写入一次但读取侧从不读（窗口统一由 `ai.memory.*` 决定），
保留列与 `chk_cs_window` 约束、只改注释——下一阶段做"记忆 token 预算"时很可能引入新的预算列，现在删了又要加。

## 会话记忆（② 期，2026-10-16 落地）：token 预算 + 滚动摘要 + 工具结果回放

**影响所有对话接口（2.23~2.25）的行为，但没有新增接口**——模型"看得到多少历史"由下面三条规则决定。

### 1) 从"条数窗口"改成"token 预算"

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `ai.memory.max-prompt-tokens` | 4096 | 一轮 prompt 允许的总 token（含系统提示词与工具定义） |
| `ai.memory.keep-recent-messages` | 6 | 无论预算多紧都至少保留这么多条最近历史（保底，宁可略超预算） |
| `ai.memory.window-messages` | 20 | 降级为**条数兜底**（与预算取小，防估算被极短消息带偏） |

- 装配顺序：**先扣固定开销**（系统提示词 + 工具定义，实测一轮几乎空的对话就已 5012 prompt tokens）→ 剩余预算从最近往回装 →
  **本轮消息永不裁剪**（裁了模型就看不见当前问题）；
- 估算器（中文 1 字≈1 token、ASCII 4 字符≈1 token）用**上一轮真实 `prompt_tokens` 做 EWMA 校准**，
  日志每轮打一行 `记忆估算校准：真实prompt_tokens=… 估算=… 当前系数=…`，这是"预算是否在收敛"的唯一可观测证据；
- 日志还会打 `会话记忆装配 sessionId=… 保留历史=… 裁剪=… 估算token=… 预算=… 摘要=… 工具摘要=…`，
  超预算时显式标注`（超预算：保底条数优先）`——不把"安全阀被击穿"藏起来。

### 2) 滚动摘要（异步）

- 触发：一轮回复落库后，若"已有消息落到窗口之外"（超出 `keep-recent-messages` 且 `id > summary_upto_msg_id`）→ 异步压缩；
- **不阻塞用户**：独立线程池 `chat-summary-*`，单飞（同一会话同时只跑一个任务）；
- **只前进**：写回带 `summary_upto_msg_id <` 条件，慢任务不会把指针拉回去（否则同一段原文被反复压缩、越压越糊）；
- **失败降级**：模型报错/返回空/写库失败都只记日志，不推进指针、不写半截摘要，窗口里仍有原文；
- 产物存在 `chat_session.context_summary`（**该列 V1 就存在，本期正式启用**），并推进 `summary_upto_msg_id`；
- 注入形式：作为**一条附加上下文 SystemMessage**（与最近工具摘要合并）放在历史之前，明确标注
  "更早对话的摘要（由系统压缩，不是你刚才说的话）"——避免模型把摘要当成用户刚说的话去回应。

### 3) 新场景 SUMMARY（会话摘要压缩）

摘要**不复用 CHAT 通道**：它需要自己的提示词（后台可改、可回滚）、自己的模型（可绑更便宜的）、自己的温度（0.1，要复述不要发挥），
而且不该带工具（摘要时去调工具=让模型查数据，破坏"只压缩原文"的语义）。
提示词见 `prompts/summary/compress.md`，迁移 V22/V23 已把 v1 播种进 `ai_prompt_template`（后台 `/ai/prompt` 可直接改）。
请求级参数由 `SceneModelResolver.summaryOptionsBuilder()` 统一给出：**关思维链 + 输出封顶（`ai.memory.summary-max-tokens`，默认 600）**
——实测 6000 字输入叠加思维链会直接读超时、摘要一直建不起来，故输入上限也从 6000 降到 3000（`ai.memory.summary-input-max-chars`）。

### 4) 工具结果回放（B3 后半）

- 工具调用落 `chat_tool_call` 时新增 `result_digest`（≤512 字）：**结构感知的压缩**
  （保留 avg/count 这类标量、长数组只留前 3 项并标注"共N项"、丢掉空值字段），**仍不存完整返回**（那是用户健康数据）；
- 装配时把最近 {@code ai.memory.tool-replay-max-items}（默认 3）条以"最近查询到的数据摘要"注入附加上下文，
  并注明"不要据此给用药建议"。目标是让模型能回答"刚才查到的数据里最高是多少"，而不是重新调一次工具。
