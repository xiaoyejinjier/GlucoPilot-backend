# 1. 引言

## 1.1. 设计目标

本库服务于真实上线的「AI 控糖助手」微信小程序（C 端）与运营后台（B 端），目标包括：

健康数据可追溯：血糖/饮食分表、九时段语义清晰，支持统计导出与合规审计。

登录与资料解耦：账号、资料、健康档案、偏好设置分表，便于权限与脱敏。

AI 对话可续聊可复现：会话摘要 + 消息原文 + 上下文切片 + 跨会话记忆。

运营可管控：RBAC、系统参数、推送任务、操作审计（只追加）。

生产可运维：无物理外键、无触发器、无存储过程；关联与业务规则由应用层事务保证，便于分库分表与在线 DDL。

## 1.2. 生产原则

| 项 | 生产约定 |
| --- | --- |
| 时间字段 | 统一 gmt_create / gmt_modified（毫秒 DATETIME(3)） |
| 逻辑删除唯一键 | (业务键, is_deleted) 联合唯一；不使用 VIRTUAL 生成列 |
| 外键 | 禁止物理 FOREIGN KEY；应用层校验存在性 |
| 触发器/存储过程 | 禁止；节点餐点语义、计数冗余等在服务端事务内完成 |
| 审计 | 业务表七件套；ops_audit_log 仅 created_by + gmt_create，只追加 |
| 枚举 | TINYINT UNSIGNED + COMMENT；对外 API 用同名数字，禁止中文字符串落库 |
| 计量 | 血糖/碳水/热量/GI 用 DECIMAL，禁止 FLOAT/DOUBLE |
| 密钥 | ai_model_config.api_key_cipher 仅密文或 KMS 引用，禁止明文 |

# 5. 应用层约束与运维约定

本 DDL 无外键、无触发器、无存储过程。下列规则必须在服务端实现：

| 序号 | 约束 |
| --- | --- |
| 1 | glucose_record.node_code → dict_glucose_node.is_meal=0 且启用 |
| 2 | meal_record.node_code → dict_glucose_node.is_meal=1 且启用 |
| 3 | user_id/ops_id/session_id/media_id/meal_id/news_id/template_id 等引用存在且未删 |
| 4 | chat_message.client_msg_id 幂等：捕获 MySQL 1062 视为成功 |
| 5 | 聊天 payload（文本/图/语音/流式占位）完整性由应用层校验 |
| 6 | 软删唯一键：同一业务键仅一条 is_deleted=0；复用前处理历史软删行 |
| 7 | ai_model_config.is_default 全局至多一个默认（事务内先清零） |
| 8 | 资讯点赞/收藏变更时同步维护 cms_news.like_count/collect_count |
| 9 | 导出/备份含健康数据：短时效下载链接 + 访问审计 |
| 10 | ops_audit_log 只追加；健康档案查看/导出强制落审计 |
| 11 | 运营口令只存 password_hash（bcrypt/argon2），禁止明文；审计/日志不得记录口令与验证码原文 |
| 12 | 短信验证码优先 Redis；auth_sms_code 若使用须短 TTL 且禁止日志打印原文 |
| 13 | api_key_cipher 禁止明文回显 |
