# 1. 产品概述

## 1.1. 背景与问题

糖尿病与高血糖人群需要长期、高频地记录血糖与饮食，并据此调整行为；现状痛点是：记录门槛高（手工录入繁琐）、缺少个体化解读（只记录不指导）、数据分散（无法形成长期档案）、依从性差（无提醒与反馈闭环）。

## 1.2. 产品定位

**面向控糖人群的「AI 控糖助手」**：以微信小程序承载用户端，以 PC 运营后台承载内容与用户服务；以"血糖 + 饮食"数据采集为基础，通过 AI 提供血糖预测、饮食建议与控糖问答，并把长期记录沉淀为个人健康档案。

业务闭环：**记录 → 分析 → 建议 → 追踪**。

## 1.3. 产品目标与成功指标

| 目标 | 成功指标（一期） |
|---|---|
| 降低记录门槛 | 九时段记录完成率 ≥ 60%；单节点记录操作 ≤ 3 步 |
| 提供个体化指导 | 拍照估糖/AI 问答可用率 ≥ 95%；用户对估算结果确认率 ≥ 80% |
| 形成长期档案 | 连续记录 ≥ 7 天用户占比 ≥ 35%；统计页周活跃 ≥ 40% |
| 平台可运营 | 资讯每周更新 ≥ 3 篇；反馈 48h 内响应率 ≥ 90% |

## 1.4. 用户与角色

| 角色 | 使用端 | 主要能力 |
|---|---|---|
| C 端用户（控糖人群/家属） | 微信小程序 | 登录、九时段血糖记录、拍照估糖/OCR、饮食记录与分析、AI 对话、统计与档案、资讯、营养库、反馈、导出与备份 |
| 运营编辑（`ROLE_EDITOR`） | PC 后台 | 资讯/轮播/媒体、食物库、反馈回复、导出任务；**不可见**用户健康明细与系统管理 |
| 系统管理员（`ROLE_ADMIN`） | PC 后台 | 全部权限，含用户管理、健康档案查看（强制审计）、角色权限、系统参数、操作日志、消息推送与 AI 配置 |

权限模型：RBAC —— `ops_account → sys_ops_role → sys_role → sys_role_permission → sys_permission(perm_code)`；前端据 `permCodes` 渲染菜单/按钮，**服务端二次校验为准**。

## 2.2. 关键业务流程

1. **九时段记录**：选择节点 → 手动输入或拍照估糖 → 展示结果（标注"估算值"）→ 用户确认/修改 → 幂等写入（`PUT …/by-node`，按日期+节点覆盖）→ 图标变色 + 曲线更新。
2. **OCR 确认入库**：拍照上传（预签名直传）→ `POST /api/v1/ocr/tasks` → 轮询 `GET /ocr/tasks/{id}` → 展示识别值 → 用户确认 → 写入血糖记录（`source` 标记来源）。
3. **饮食分析**：拍照 → 分析（食物+碳水+当前预测）→ 建议量 → 按建议再预测 → 语音补充 → 重新分析 → 保存饮食记录与明细。
4. **AI 对话**：进入语音页 → 获取/创建会话 → 发送消息（`clientMsgId` 幂等）→ SSE 流式返回 → 落库消息 + 更新会话摘要/上下文/长期记忆。
5. **档案与导出**：记录日聚合 → 日历/周趋势/摘要 → 创建导出任务（异步生成）→ 短时效下载（含审计）；支持备份与恢复。
6. **后台闭环**：运营回复反馈并流转状态 → 管理员查看健康档案（**强制写 `ops_audit_log`**）。

## 2.3. 业务规则与红线

| 规则 | 说明 |
|---|---|
| AI 可自动识别，用户必须确认 | OCR/估糖结果展示后可修改，确认后才入库；界面标注"估算值/仅供参考" |
| 健康数据最小可见 | 健康明细仅管理员可查看，且每次查看/导出强制审计 |
| 医疗边界 | 不提供诊断与处方；各处显著免责声明 |
| 无商城、无好友聊天 | 一期不含交易与社交；无商户后台 |
| 用户端形态 | 微信小程序；不单独发布 App、不做 PC 用户前台 |
| 数据合规 | 手机号脱敏展示、密钥密文存储、验证码不落日志 |

# 4. 技术路线

## 4.1. 总体架构

```
微信小程序（C端）  ─┐
                    ├─→  API 网关 /api/v1  ─┐
PC 运营后台（B端） ─┴─→  API 网关 /admin/v1 ─┴─→  应用服务（Spring Boot 3）
                                                   ├─ MySQL 8.0.16+（sugar_health，38 表）
                                                   ├─ Redis（会话/验证码/限流/幂等）
                                                   ├─ 对象存储 OSS（媒体、导出、备份）
                                                   └─ AI 服务（OCR / LLM / ASR / TTS）
```

## 4.2. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| C 端 | 微信小程序（`glass-easel`，自定义 TabBar，5 Tab：首页/语音/AI/统计/我的） | 开发工具：微信开发者工具；接口统一走 HTTPS |
| B 端 | Vue3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + ECharts | 现工程 `控糖健康管理系统/admin-web`；设计令牌与小程序一致 |
| 服务端 | Spring Boot 3.x + JDK 17 + MyBatis-Plus/JPA + Maven | 统一响应 `ApiResult`；包结构 `controller/service/mapper|repository/entity/dto/common` |
| 数据库 | MySQL 8.0.16+（`utf8mb4`，InnoDB，无外键/触发器/存储过程） | 38 张表，见数据库设计文档 |
| 缓存 | Redis | 会话、短信验证码、登录锁定、限流、幂等键、热点配置 |
| 存储 | 对象存储 + CDN | 媒体直传；导出/备份短时效链接 |
| AI | OCR 服务 + LLM（对话/分析）+ ASR/TTS | 模型与提示词入库可配（`ai_model_config`/`ai_prompt_template`） |
| 消息 | 微信订阅消息 | 模板/任务/明细三表管理 |
| 运维 | 容器化部署 + Nginx + 日志/监控告警 | 环境 dev/test/prod 三套 |

## 4.3. AI 能力实现要点

- **OCR 任务化**：`ocr_task` 记录任务状态与 `ocr_result_json`（含 `schemaVersion`），前端轮询展示，用户确认后写业务表；
- **饮食分析**：识别 + 营养库匹配 + 个体化预测（当前 vs 建议），支持语音补充后重算；
- **对话**：`chat_session`（滚动摘要与窗口参数）+ `chat_message`（含 token 计量）+ `chat_context`（窗口切片）+ `chat_user_memory`（跨会话长期记忆）；输出走 SSE；
- **配置化**：模型参数与提示词模板由后台维护，支持灰度切换与回滚。

# 5. 开发规范

| 维度 | 规范 |
|---|---|
| 后端 | 遵循《阿里巴巴 Java 开发手册（泰山版）》：命名、异常、日志、集合、并发、数据库（禁用外键/触发器、必备审计字段、`SELECT` 禁用 `*`） |
| 前端 | 遵循《阿里巴巴前端开发规范》：目录与命名（组件 PascalCase、常量 UPPER_SNAKE、组合式函数 `useXxx`）、ESLint + Prettier + stylelint、Git 提交 `type(scope): subject`；细则见 `docs/ADMIN-FRONTEND-SPEC.md` |

| 文档 | 需求（本 PRD）、接口、数据库、UI 四套文档与代码同仓维护，变更同步更新 |

# 6. 数据库设计（摘要，以《数据库设计文档》为准）

## 6.1. 基线

| 项 | 内容 |
|---|---|
| 库名 | `sugar_health` |
| 版本 | MySQL 8.0.16+（支持 CHECK 约束） |
| 表数量 | **38 张** |
| 字符集 | `utf8mb4` / `utf8mb4_unicode_ci`，InnoDB |
| DDL | `docs/智能健康管理助手数据库设计-merged-v2.sql` |

## 6.2. 生产原则（强制）

- 时间统一 `gmt_create` / `gmt_modified`（`DATETIME(3)`）；
- 逻辑删除 `is_deleted` + `deleted_at` + `deleted_by`（CHECK 一致性）；软删唯一键 `(业务键, is_deleted)` 联合唯一，不使用 VIRTUAL 生成列；
- **禁止**物理外键、触发器、存储过程；关联与业务规则由应用层事务保证；
- 枚举 `TINYINT UNSIGNED` + `COMMENT`，对外 API 用同名数字；
- 计量（血糖/碳水/热量/GI）用 `DECIMAL`；
- 审计：业务表七件套；`ops_audit_log` 仅 `created_by + gmt_create`，只追加；
- 密钥：`ai_model_config.api_key_cipher` 仅密文或 KMS 引用；
- 备份：每日全量 + binlog；健康与导出文件走对象存储生命周期。

## 6.3. 表清单（38 张，按模块）

| 模块 | 表 |
|---|---|
| 字典 | `dict_glucose_node` |
| C 端用户 | `user_account`、`user_profile`、`user_health`、`user_setting`、`user_session`、`auth_sms_code` |
| 运营 RBAC | `ops_account`、`ops_profile`、`sys_role`、`sys_permission`、`sys_ops_role`、`sys_role_permission`、`ops_session` |
| 核心业务 | `media_file`、`glucose_record`、`meal_record`、`meal_food_item`、`chat_session`、`chat_message`、`chat_context`、`chat_user_memory`、`feedback`、`ocr_task` |
| 内容与工具 | `food_category`、`food_nutrition`、`cms_banner`、`cms_news`、`news_user_action`、`data_export_task`、`data_backup` |
| AI 与推送 | `sys_config`、`ai_model_config`、`ai_prompt_template`、`msg_push_template`、`msg_push_task`、`msg_push_record` |
| 审计 | `ops_audit_log` |

## 6.4. 应用层约束（必须在服务端实现）

1. `glucose_record.node_code` 必须指向 `dict_glucose_node.is_meal=0` 且启用的节点；`meal_record.node_code` 对应 `is_meal=1`；
2. 所有 `user_id/ops_id/session_id/media_id/meal_id/news_id/template_id` 引用需校验存在且未删；
3. `chat_message.client_msg_id` 幂等（捕获 MySQL 1062 视为成功）；
4. 软删唯一键：同一业务键仅一条 `is_deleted=0`，复用前先处理历史软删行；
5. `ai_model_config.is_default` 全局至多一个（事务内先清零）；
6. 点赞/收藏变更同步维护 `cms_news.like_count/collect_count`；
7. 导出/备份含健康数据：短时效下载链接 + 访问审计；
8. `ops_audit_log` 只追加；**健康档案查看/导出强制落审计**；
9. 运营口令只存哈希；审计与日志不得记录口令、验证码原文；`api_key_cipher` 禁止明文回显；
10. 短信验证码优先 Redis，`auth_sms_code` 若使用须短 TTL。

## 6.5. 视图 / JSON 契约

- 视图、触发器、存储过程本期均**不建**；统计走应用聚合或离线数仓；
- 以下 JSON 列必须含 `schemaVersion`（整型，从 1 起），变更只能追加字段或升版本：`ocr_task.ocr_result_json`、`data_backup.payload_json`、`msg_push_task.target_json/payload_json`；`chat_context.content_json` 为服务端内部契约，对外不承诺稳定。

# 7. 接口设计（摘要，以《接口设计文档》为准）

## 7.1. 全局约定

| 项 | 约定 |
|---|---|
| 前缀 | C 端 `/api/v1`；B 端 `/admin/v1`；路径为小写连字符名词复数（如 `/glucose-records`） |
| 报文 | 默认 `application/json;charset=UTF-8`；上传 `multipart/form-data`；AI 补全 `text/event-stream`（SSE） |
| 鉴权 | `Authorization: Bearer {accessToken}`；C 端 → `user_session`（默认 7 天，无 refreshToken）；B 端 → `ops_session`（默认 2 小时可滑动续期）+ RBAC `perm_code` |
| 统一响应 | `{ code, message, data, requestId }`；成功 HTTP 200 且 `code=0` |
| 字段命名 | 对外 camelCase，库内 snake_case；枚举库与 API 统一数字 |
| 分页 | 请求 `pageNum`/`pageSize`（最大 100）；响应含 `pageNum/pageSize/total/pages/records`；字典/轮播/分类等非分页全量返回 |
| 幂等 | 聊天消息强制 `clientMsgId`；九时段写入 `PUT …/by-node` 按日期+节点覆盖；导出/备份/OCR 创建与后台发布/回复/推送执行使用 `X-Idempotency-Key` |
| 更新语义 | `PATCH` 省略字段=不改，显式 `null`=置空 |
| 会话失效 | 登出或账号禁用将 `is_valid` 置 0 |

## 7.2. 错误码（HTTP 三位 + body 五位）

| HTTP | code | 含义 |
|---|---|---|
| 200 | 0 | 成功 |
| 400 | 40000 | 参数格式/类型/必填校验失败 |
| 400 | 40001 | 业务校验失败或凭证错误 |
| 401 | 40100 | 未登录或 Token 失效 |
| 403 | 40300 | 无权限、账号禁用或注销中 |
| 404 | 40400 | 资源不存在或不属于当前用户 |
| 409 | 40900 | 冲突（唯一键、乐观锁、账号占用） |
| 429 | 42901 | 限流或登录锁定 |
| 500 | 50000 | 系统异常 |

## 7.3. 接口清单（39 个）

**C 端（36 个，`/api/v1`）**：微信登录、发送短信验证码、手机号登录、微信绑定、退出登录、获取当前用户信息、更新用户资料、保存健康档案、更新偏好设置、同意免责声明、绑定手机号、九时段节点字典、公开配置、媒体上传凭证、登记媒体文件、日看板查询、血糖记录幂等写入、血糖统计摘要、饮食记录幂等写入、饮食分析、创建 OCR 任务、查询 OCR 任务、获取或创建当前会话、发送聊天消息、AI 流式补全、首页 Banner 列表、资讯列表、资讯详情、食物分类列表、食物营养列表、提交反馈、我的反馈列表、创建导出任务、导出任务详情与下载、创建数据备份、恢复数据备份。

**B 端（3 个，`/admin/v1`，已定义）**：

| 接口 | 方法与路径 | 权限 | 关键约束 |
|---|---|---|---|
| 运营后台登录 | `POST /admin/v1/auth/sessions` | 匿名 | 口令仅 HTTPS 传输、哈希比对；错误统一 `40001` 防枚举；停用 `40300`；连续失败锁定 |
| 运营回复反馈 | `PATCH /admin/v1/feedbacks/{id}` | `feedback:reply` | 入参 `replyStatus`(0 已收到/1 处理中/2 已处理/3 已关闭) + `officialReply`；写 `ops_audit_log` |
| 运营查看用户健康档案 | `GET /admin/v1/users/{id}/health-archive` | `health:archive:view` | 敏感读；成功**强制写审计** |

**B 端待扩展（按同一规范落地）**：资讯/轮播/媒体管理、食物分类与营养库维护、用户列表与禁用、导出任务处理、消息推送（模板/任务/明细）、AI 模型与提示词配置、系统参数、审计日志查询。扩展清单与字段建议见 `docs/ADMIN-API.md`，须与 `ops_*`/`sys_*` 表结构保持一致。

## 7.4. 与数据库的边界

- C 端/B 端共库（`sugar_health`）、共枚举；血糖与饮食**分表存储**，读聚合走日看板接口，**禁止前端混存模型直写库**；
- 绑定、OCR/摘要/SSE/备份等契约细节以《设计决策与协作约定》与专项文档为准。

## 8.4. 质量门禁（DoD）

- 代码：静态检查与类型检查通过；评审通过；无 `SELECT *`、无明文密钥/口令；
- 接口：与接口文档一致（路径/字段/错误码/权限）；幂等与分页符合规范；
- 数据库：变更提供 DDL + 回滚方案；索引覆盖高频查询；审计与软删规则落实；
- 测试：核心流程（登录→记录→分析→统计→后台回复/档案查看）用例通过；权限可见性双角色验证；
- 文档：需求/接口/数据库/UI 文档同步更新。

## 8.5. 合规与安全约束

- 健康数据属敏感个人信息：最小化采集、明示同意、可删除、访问留痕；
- 非医疗器械定位，不提供诊断/处方，全链路免责声明；
- 手机号等展示脱敏；导出/备份短时效链接且审计；
- 短信/推送频控；验证码与密钥不落日志。

## 8.6. 变更管理

| 变更类型 | 流程 |
|---|---|
| 需求变更 | 提变更单 → 评估影响（范围/排期/测试）→ 产品负责人确认 → 更新 PRD 与任务 |
| 接口变更 | 更新接口文档 → 前后端同步 → 兼容期内双版本并存 → 观察后下线旧版本 |
| 数据库变更 | 提交 DDL + 影响评估 + 回滚脚本 → DBA/负责人评审 → 低峰期执行 |
| 上线回滚 | 保留上一版本镜像与配置；数据变更需可回滚或前向修复 |

## 8.7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| OCR/估糖准确率不足 | 用户信任下降 | 结果标注"估算值"+用户确认机制；持续用真实数据评估阈值 |
| AI 输出幻觉 | 合规与体验风险 | 提示词约束 + 免责声明 + 人工审核抽检 + 敏感问题引导就医 |
| 健康数据合规 | 法律风险 | 权限最小化、强制审计、脱敏、可删除、法律评审 |
| 第三方服务中断 | 功能不可用 | 降级策略（手动录入）、重试与熔断、服务多供应商评估 |
| 排期与人力 | 延期 | P0/P1 分层交付；每周进度复盘；关键路径提前介入 |
